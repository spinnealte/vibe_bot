# Ревью кода бота (03.11.2026, FullWebTelegramBot)

Проверен весь код полной версии (копия fullbot, коммит b2f6c3b): сервисы и репозитории, хендлеры, тексты,
миграции, фоновые задачи (напоминания, сверка онлайн-оплаты), тесты. Перед переносом функций в веб-приложение
важно было убедиться, что правила записи и оплаты живут в сервисах, а не в хендлерах: так и есть - приложение
зовёт те же сервисы, своих правил у него нет.

## Найдено и исправлено

1. **Программа курса на первой странице могла не поместиться.** Заголовок курса занимает место только на первой
   странице, а делилась программа по одной границе для всех страниц - первая выходила длиннее лимита Telegram.
   Теперь у первой страницы своя граница (`render.split_html(first_limit=…)`). Тест
   `test_program_title_takes_room_only_on_the_first_page`.
2. **Заказ без суммы считал срок оплаты.** У курса без цены сумму называет менеджер, но 72 часа шли с момента
   записи: через сутки уходило напоминание, через 72 часа - «просрочено», а клиенту обещали срок, которого нет.
   Теперь у такого заказа срока нет, пока менеджер не назовёт сумму (`AdminOrderService.set_total` ставит срок
   от этого момента и сбрасывает отметки напоминаний); напоминания и «просрочено» - только заказам с суммой;
   тексты говорят «72 часа с момента, когда менеджер назовёт сумму». Тесты в test_admin_orders и test_e2e_admin.
3. **Реквизиты принимались любым файлом.** Клиент мог прислать `.exe`, и бот переслал бы его админам. Теперь -
   только документы и картинки до 20 МБ (`utils/files.py`, `REQUISITES_EXTENSIONS`); иначе подсказка, какие файлы
   подходят. Тест в test_e2e_client.
4. **Контакт вне регистрации получал ответ «не понимаю».** Нужно для приложения: «Поделиться номером» в Mini App
   Telegram дублирует контактом в чат с ботом. Теперь такой контакт бот молча пропускает
   (`fallback.contact_outside_steps`). Тест в test_e2e_inputs и test_web_api.

## Доработано для веб-приложения (поведение бота не меняется)

- `ConsentService.grant(..., source)` и `EnrollmentService.enroll(..., source)` - откуда согласие и запись:
  бот (как раньше) или приложение (`site`). В выгрузке и в базе видно, где человек записался.
- `ScheduleService.cards` - вся афиша двумя запросами (для списка в приложении), бот листает по-прежнему.
- `connect_args(schema)` и `DB_SCHEMA` - своя схема в базе для разработки (search_path), прод - как был.

## Проверено, замечаний нет

- Доступ: админ-роутер под фильтром целиком; поддельные данные кнопок (чужие id, числа больше bigint) - «кнопка
  неактуальна»; чужие заказы и записи ищутся только среди своих.
- Деньги: копейки, блокировки в одном порядке (заказ → записи), двойные нажатия не создают второй платёж или
  запись, онлайн-оплата применяется один раз.
- Ввод: HTML пользователя экранируется, NUL вычищается до хендлеров, длинные тексты делятся на страницы.
- Логи: без ПД и секретов (это проверяют сквозные сценарии после каждого прогона).

## На заметку (не ошибки, решать по ходу)

- Поиск клиентов по ФИО зависит от локали базы: с `lc_ctype=C` он станет чувствителен к регистру (проверить на
  боевой базе при выкатке).
- Защита от флуда и ограничение запросов приложения - в памяти процесса: при нескольких копиях приложения
  счётчики у каждой свои.
- После онлайн-оплаты ЮKassa возвращает человека в чат с ботом; для приложения лучше вернуть в само приложение
  (ссылка `t.me/<бот>/<приложение>`) - когда у приложения будет постоянный адрес.

Итог прогона 03.11.2026 (с админкой в приложении): 466 тестов (бот - 444, приложение - 22), все проходят; сквозные сценарии вызывают
все 148 хендлеров бота.
