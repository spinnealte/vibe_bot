# stubBot - Telegram-бот учебного центра (MVP)

## Эта папка - полная версия (ветка `full`)
Здесь, в `D:\ClaudeBotAi\fullbot`, разрабатывается **полная версия** бота. MVP живёт рядом, в `../stubBot`
(ветка `main`), и должен оставаться готовым к деплою без изменений, пока идёт согласование с заказчиком.
Обе папки - один репозиторий (git worktree), поэтому коммиты отсюда идут в ветку `full`.
- Функции полной версии - только здесь. Из этой папки файлы в `../stubBot` не менять.
- Правка для MVP делается в `../stubBot` (ветка `main`), потом подтягивается сюда: `git merge main`.
  В обратную сторону (`full` → `main`) ничего не переносится до выпуска полной версии.
- Своя база `stubbot_full`, своя база Redis (номер 1), свой тестовый бот @fulldemotest_bot - всё в `.env`
  этой папки. База и токен MVP отсюда не используются.
- Всё, что ниже, написано про MVP и остаётся в силе как основа: правила, стек, история решений.
  План полной версии - в конце раздела «План…» («После MVP»); этап 1 (запись и оплата) расписан там же.

## Что это

Бот-заглушка учебного центра для стоматологов (Санкт-Петербург, разные площадки).
Цель: начать накапливать базу клиентов для маркетинга до выхода полного бота.
Полный бот позже будет работать **на том же токене и той же БД**, поэтому схема БД проектируется сразу под полный функционал
(MVP создаёт часть таблиц, остальное добавляется только аддитивными миграциями).

Соседняя папка `../mainDirectory` - старый прототип полного бота. Использовать только как справочник по сценариям
(особенно мастер добавления курса в админке). Код не копировать: разбор его проблем в `docs/00_code_review_mainDirectory.md`.

## Документы (читать перед работой)

- `docs/01_db_plan.md` - утверждённый план БД v1.1 (таблицы [MVP] и [FULL], соглашения, журнал решений). Источник истины по схеме.
- `docs/00_code_review_mainDirectory.md` - ошибки старого бота, которые нельзя повторять.

## Стек

Python 3.12+, aiogram 3.x, PostgreSQL + SQLAlchemy 2.0 async + asyncpg, Alembic, Redis (FSM storage), pydantic-settings.
Разработка на Windows (Redis в WSL). Зависимости фиксировать полностью (requirements с версиями или uv/poetry lock).
Docker сами не используем - никогда и ни при каких обстоятельствах: Dockerfile не пишем, Docker не ставим и не запускаем.
Прод - на Amvera (российский PaaS, регион Москва; решение 06.10.2026): PostgreSQL, Redis и приложение - три проекта
в одном аккаунте, обновление - `git push amvera main:master`, инструкция - `deploy/AMVERA.md`. Контейнеры Amvera
собирает сама из `amvera.yml`. Свой туннель до Telegram не нужен: Amvera сама направляет обращения к Telegram
через иностранный адрес. Запасной способ - свой сервер (`deploy/README.md`).

## Функционал MVP

MVP - афиша + личный кабинет для старта маркетинга. Записи/заявок внутри бота нет.
Пользователь:

- /start с диплинками: `src_<code>` (источник трафика: листовки QR, сайт, VK, Instagram, TG-канал), `ref_<code>` (реферал), `inv_<token>` (приглашение, FULL). Каждый заход пишется в client_source_touches.
- Экран согласий: ПД (обязательно) и рекламные рассылки (отдельно, опционально). Тексты - из legal_documents.
- Короткая регистрация: телефон кнопкой «Поделиться контактом», ФИО (одно текстовое поле, подтверждение для сертификата), специальности, должность. Остальное - дозаполнение в кабинете.
- Личный кабинет: профиль и редактирование, реферальная ссылка + счётчик.
- Расписание (просмотр): ближайшие потоки, карточка, программа, даты/время по дням, площадка, тарифы.
  Под каждым курсом - кнопка записи, которая открывает диалог с менеджером (ссылку на менеджера пользователь даст позже).
- Заявки, «Мои заявки», «Сообщить о наборе» - код есть, но выключены (APPLICATIONS_ENABLED=false) до полной версии.
- О центре / контакты / связаться с менеджером.
  Админ (роли из таблицы admins, owner - из .env):
- Справочники: лекторы, площадки, специальности, должности.
- Мастер «Новый курс» (programs) и мастер «Новый поток» (sessions + session_days + тарифы + лекторы), кнопка «Скопировать прошлый поток».
- Уведомление менеджерам о новой заявке, смена статуса заявки.
- /stats: новые пользователи по дням и по источникам, заявки. Экспорт клиентов в CSV.
- Генерация ссылок источников (acquisition_sources).

## Обязательные правила (выводы из ревью старого бота)

- Фильтр админа на уровне всего админ-роутера (message и callback_query), не на отдельных хендлерах.
- Любой пользовательский текст в HTML - через html.escape. Длинные тексты не в caption (лимит 1024), при необходимости фото и текст отдельно.
- FSM-шаги, ожидающие текст, должны корректно обрабатывать фото/стикеры/голос.
- Глобальный обработчик ошибок `dp.errors`, без глотающих middleware.
- Никаких ПД и секретов в логах и print(). INFO на проде.
- Имя бота для ссылок - из `await bot.me()`, не хардкод.
- Только Alembic-миграции; create_all / DROP SCHEMA на проде запрещены. Naming convention в MetaData.
- Callback data - через `CallbackData`-фабрики, не строки со split.
- Любая inline-кнопка меняет то сообщение, в котором нажата (насколько позволяют aiogram/Telegram): текст→текст,
  фото→фото - правка; фото↔текст или сообщение удалено - удалить старое и прислать новое.
- Расписание - карусель со стрелками ◀️ n/N ▶️ (обязательно).
- Слой доступа к данным: репозитории/сервисы по доменам; сессия БД на апдейт через middleware. Хендлеры без SQL.
- Нет копипасты однотипных редакторов полей - generic-реализация.
- Проверять результаты операций (запись на поток, дубликаты, статус потока).
- Время - TIMESTAMPTZ, Europe/Moscow в интерфейсе; деньги в копейках; enum через native_enum=False.

## Порядок работы

1. Скелет проекта: структура пакетов, конфиг, логирование (Postgres локально, Redis в WSL - без Docker).
2. Модели MVP-таблиц строго по docs/01_db_plan.md + первая миграция Alembic + сиды справочников.
3. Регистрация, согласия, источники → кабинет → расписание и заявки → админка → статистика.
   Перед каждым этапом кратко предложить план и дождаться подтверждения.

- Моё предложение, пользователь не возражал: «Подтвердить получение» - переключатель перед отправкой, по умолчанию включён.

План по шагам (словом «да» не утверждён; перед началом показать ещё раз):
- Шаг 1. Раздел «👥 Участники»: «🔎 По ФИО» (часть ФИО от 2 букв, до 30 результатов, рядом с ФИО - последние
  4 цифры телефона) и «🗓 По проведению» (месяц → проведение → список). Карточка клиента: ФИО, телефон, его записи,
  пометки «бот заблокирован» и «согласие на рассылки: да/нет», кнопка «✉️ Написать».
- Шаг 2. Таблицы учёта и личное сообщение: админ присылает одно сообщение (текст либо файл/фото с подписью) →
  предпросмотр тем же способом, каким уйдёт получателю, + получатель → «✅ Отправить / ✏️ Изменить / ✖️ Отмена» →
  админу «✅ Доставлено» или «❌ Не доставлено» с причиной. Нажатие «Подтвердить получение» меняет кнопку на
  «✅ Получено» и уведомляет админа.
- Шаг 3. Напоминание участникам: в карточке проведения «🔔 Напомнить участникам · N» → готовый текст из карточки
  (название, даты, время начала, адрес, карта) или свой текст/файл → предпросмотр и число получателей →
  «🚀 Отправить (N)». Отправка в фоне со счётчиком, в конце отчёт (доставлено / заблокировали бота / ошибка)
  и список тех, кому не дошло.
- Шаг 4. Журнал «📨 Сообщения»: что, кому и когда ушло, статусы по каждому получателю.

База (раздел G в docs/01_db_plan.md, миграция только добавляет таблицы):
- campaigns - одно отправление: вид (личное / по проведению), session_id, Telegram ID отправившего админа
  (таблица admins пока не используется), текст, вложение (вид, file_id, имя файла), была ли кнопка подтверждения,
  статус (идёт / завершено / прервано), счётчики, время.
- campaign_recipients - строка на получателя: client_id, статус отправки (ждёт / доставлено / бот заблокирован /
  ошибка), причина ошибки, telegram_message_id, sent_at, confirmed_at. Личное сообщение - отправление с одним получателем.

Код: db/models/messaging.py; repositories/ и services/participants.py; services/messaging.py; services/mailer.py
(одна функция «доставить одному» для личных и массовых, очередь массовых в фоне, не быстрее 20 сообщений в
секунду, свои короткие транзакции: «ждёт» → результат); tg/outgoing.py (отправка содержимого, ею же предпросмотр);
tg/handlers/admin_people.py и admin_messages.py под фильтром «только админ»; tg/handlers/receipt.py (кнопка
клиента, работает на любом шаге его сценария); запуск и остановка отправщика в __main__.py.

Что обязательно учесть (разбор рисков 11.10.2026):
- «Подтвердить получение» с чужим номером в кнопке - проверять, что строка получателя принадлежит нажавшему.
- Двойное нажатие «Отправить» - черновик расходуется один раз.
- Массовая отправка только фоновой задачей (в обработчике она заморозит админку); паузы и ожидание по требованию
  Telegram; результат пишется по каждому получателю; после перезапуска - «прервано, отправлено 12 из 30,
  продолжить?» (один человек может получить дубль).
- Перед массовой отправкой: название проведения и число получателей на кнопке; предупреждение, если напоминание
  по этому проведению сегодня уже уходило.
- Ввод: подпись к файлу не длиннее 1024 знаков; альбом, голосовое, стикер - отказ с подсказкой.
- Поиск по ФИО: экранировать % и _, удалённых клиентов не показывать.
- В логах только номера записей; текст сообщений и ФИО не пишутся. Действия админа - в admin.log.
- «Доставлено» - это «Telegram принял», о прочтении бот не знает; единственный сигнал - кнопка.
- Под сообщением вторая кнопка «💬 Написать менеджеру» (если задан MANAGER_URL): ответ боту до админа не дойдёт.
- Подтверждения по массовой отправке - счётчиком в журнале, без уведомления на каждого.
- Напоминание по своему курсу - сервисное; реклама - только тем, кто дал согласие на рассылки.
