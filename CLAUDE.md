# stubBot — Telegram-бот учебного центра (MVP)

## Что это
Бот-заглушка учебного центра для стоматологов (Санкт-Петербург, разные площадки).
Цель: начать накапливать базу клиентов для маркетинга до выхода полного бота.
Полный бот позже будет работать **на том же токене и той же БД**, поэтому схема БД проектируется сразу под полный функционал
(MVP создаёт часть таблиц, остальное добавляется только аддитивными миграциями).

Соседняя папка `../mainDirectory` — старый прототип полного бота. Использовать только как справочник по сценариям
(особенно мастер добавления курса в админке). Код не копировать: разбор его проблем в `docs/00_code_review_mainDirectory.md`.

## Документы (читать перед работой)
- `docs/01_db_plan.md` — утверждённый план БД v1.1 (таблицы [MVP] и [FULL], соглашения, журнал решений). Источник истины по схеме.
- `docs/00_code_review_mainDirectory.md` — ошибки старого бота, которые нельзя повторять.

## Стек
Python 3.12+, aiogram 3.x, PostgreSQL + SQLAlchemy 2.0 async + asyncpg, Alembic, Redis (FSM storage), pydantic-settings.
Разработка на Windows (Redis в WSL). Зависимости фиксировать полностью (requirements с версиями или uv/poetry lock).
Docker не используем: прод собирается вручную на VPS в РФ, Postgres и Redis ставятся на сервер напрямую.

## Инфраструктура: доступ к Telegram API из РФ
- Прод-сервер ходит к api.telegram.org через туннель: заграничный VPS с x-ui (VLESS + Reality, 443/tcp, flow xtls-rprx-vision,
  dest/SNI addons.mozilla.org) ← sing-box на РФ-сервере, локальный вход mixed 127.0.0.1:1080.
  В прокси идут только домены и подсети Telegram, остальное direct. Резерв — второй заграничный сервер с такой же настройкой.
- В коде: необязательная `TELEGRAM_PROXY_URL` (например `socks5://127.0.0.1:1080`). Пусто — напрямую (локальная разработка),
  задана — `AiohttpSession(proxy=...)` в `Bot(session=...)`, зависимость aiohttp_socks.
- Таймауты и ретраи с backoff для запросов к Bot API: кратковременный сбой туннеля не должен ронять бота.
- При старте проверка связи через `bot.me()`, в лог только «OK» и @username (без токена, ПД, URL с секретами).
- Ошибки сети — в глобальном `dp.errors`.
- `deploy/tunnel/`: шаблон sing-box config.json (mixed-вход, VLESS+Reality outbound, правила для telegram.org, t.me, telegram.me
  и подсетей 149.154.160.0/20, 91.108.4.0/22, 91.108.8.0/22, 91.108.12.0/22, 91.108.16.0/22, 91.108.20.0/22, 91.108.56.0/22,
  95.161.64.0/20, final: direct), `check-tunnel.sh` (статус sing-box, порт 1080, getMe через прокси, время ответа,
  обычный IP сервера не заграничный), README на русском: развёртывание и что делать, если туннель упал.
  Реальных ключей, UUID и IP в репозитории нет — только плейсхолдеры.
- Автопереключение на резерв (sing-box urltest/selector с двумя VLESS-исходящими) — только предложить, не внедрять без ответа.

## Принятые решения по MVP
- План БД — v1.1 (`docs/01_db_plan.md`).
- Расписание доступно без согласия; согласие на ПД — перед вводом любых персональных данных.
- Регистрация. Обязательно: телефон (только кнопкой «Поделиться контактом»), ФИО одним сообщением
  (хранится одним полем full_name, регистр не меняем; на подтверждении явно пишем, что так пойдёт в сертификат),
  специальности, должности. После — необязательные поля, каждое с «Пропустить»: город → место работы →
  опыт (спрашиваем в годах, храним practice_since_year) → email → дата рождения. Кабинет показывает все поля.
- Своих («кастомных») специальностей нет — только выбор из справочника.
- Согласия до появления настоящих текстов — временная версия «0» (создаётся сидами в LEGAL_DOCS_DIR).
- Должностей у клиента может быть несколько (client_positions). Сиды справочников — из старого бота:
  должности: Главный врач, Директор, Заместитель директора, Врач, Ассистент врача, Медсестра / Медбрат, Администратор,
  Старший администратор, Менеджер, Владелец, Учредитель;
  специальности: Хирургия, Имплантация, ЧЛХ, Анестезия, Ортопедия, Гнатология, Ортодонтия, Пародонтология, Терапия,
  Гигиена, Зуботехника, Управление, Сервис.
- Админ пока один — owner из .env; таблица admins и роли остаются в схеме.
- Тексты юридических документов пока нет: под них выделена директория (путь задаётся в конфиге), на VPS файлы кладутся туда.
- Отложено: куда слать уведомления о заявках, «Связаться с менеджером». QR-коды в боте не делаем.

## Функционал MVP
Пользователь:
- /start с диплинками: `src_<code>` (источник трафика: листовки QR, сайт, VK, Instagram, TG-канал), `ref_<code>` (реферал), `inv_<token>` (приглашение, FULL). Каждый заход пишется в client_source_touches.
- Экран согласий: ПД (обязательно) и рекламные рассылки (отдельно, опционально). Тексты — из legal_documents.
- Короткая регистрация: телефон кнопкой «Поделиться контактом», ФИО (одно поле, подтверждение для сертификата), специальности, должность. Остальное — дозаполнение в кабинете.
- Личный кабинет: профиль и редактирование, мои заявки, реферальная ссылка + счётчик.
- Расписание (просмотр): ближайшие потоки, карточка, программа, даты/время по дням, площадка, тарифы.
  Кнопки «Оставить заявку» (enrollment status=application, опция «с коллегами» → requested_seats) и «Сообщить о наборе» (program_interests).
- О центре / контакты / связаться с менеджером.
Админ (роли из таблицы admins, owner — из .env):
- Справочники: лекторы, площадки, специальности, должности.
- Мастер «Новый курс» (programs) и мастер «Новый поток» (sessions + session_days + тарифы + лекторы), кнопка «Скопировать прошлый поток».
- Уведомление менеджерам о новой заявке, смена статуса заявки.
- /stats: новые пользователи по дням и по источникам, заявки. Экспорт клиентов в CSV.
- Генерация ссылок источников (acquisition_sources).

## Обязательные правила (выводы из ревью старого бота)
- Фильтр админа на уровне всего админ-роутера (message и callback_query), не на отдельных хендлерах.
- Любой пользовательский текст в HTML — через html.escape. Длинные тексты не в caption (лимит 1024), при необходимости фото и текст отдельно.
- FSM-шаги, ожидающие текст, должны корректно обрабатывать фото/стикеры/голос.
- Глобальный обработчик ошибок `dp.errors`, без глотающих middleware.
- Никаких ПД и секретов в логах и print(). INFO на проде.
- Имя бота для ссылок — из `await bot.me()`, не хардкод.
- Только Alembic-миграции; create_all / DROP SCHEMA на проде запрещены. Naming convention в MetaData.
- Callback data — через `CallbackData`-фабрики, не строки со split.
- Inline-кнопка меняет то сообщение, в котором нажата (`tg/screen.py: show_screen`): фото→фото — edit_media,
  текст→текст — edit_text, фото↔текст — удалить и прислать новое; удалённое/старое сообщение — прислать новое.
  Новым сообщением — только ответ на текст пользователя (у вопроса убрать кнопки) и экраны с reply-клавиатурой.
- Расписание — одна карусель с фото (◀️ n/N ▶️): потоки по дате, затем курсы «даты уточняются». Подпись ≤ 1024
  (описание обрезается), подробности — кнопками «Подробнее» / «Программа». Нет фото — заглушка assets/default_cover.png.
- Слой доступа к данным: репозитории/сервисы по доменам; сессия БД на апдейт через middleware. Хендлеры без SQL.
- Нет копипасты однотипных редакторов полей — generic-реализация.
- Проверять результаты операций (запись на поток, дубликаты, статус потока).
- Время — TIMESTAMPTZ, Europe/Moscow в интерфейсе; деньги в копейках; enum через native_enum=False.

## Порядок работы
1. Проектирование БД: модели MVP-таблиц строго по docs/01_db_plan.md + первая миграция Alembic + сиды справочников
   (с минимальным каркасом, нужным для моделей: конфиг, db-пакет).
2. Скелет бота: структура пакетов, конфиг с TELEGRAM_PROXY_URL, логирование, .env.example, зависимости с версиями, deploy/tunnel/.
3. Регистрация, согласия, источники → кабинет → расписание и заявки → админка → статистика.
Перед каждым этапом кратко предложить план и дождаться подтверждения.
