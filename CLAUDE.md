# stubBot — Telegram-бот учебного центра (MVP)

## Что это
Бот-заглушка учебного центра для стоматологов (Санкт-Петербург, разные площадки).
Цель: начать накапливать базу клиентов для маркетинга до выхода полного бота.
Полный бот позже будет работать **на том же токене и той же БД**, поэтому схема БД проектируется сразу под полный функционал
(MVP создаёт часть таблиц, остальное добавляется только аддитивными миграциями).

Соседняя папка `../mainDirectory` — старый прототип полного бота. Использовать только как справочник по сценариям
(особенно мастер добавления курса в админке). Код не копировать: разбор его проблем в `docs/00_code_review_mainDirectory.md`.

## Документы (читать перед работой)
- `docs/01_db_plan.md` — утверждённый план БД v1.1 (таблицы [MVP] и [FULL], соглашения, журнал решений). Источник истины по схеме.
- `docs/00_code_review_mainDirectory.md` — ошибки старого бота, которые нельзя повторять.

## Стек
Python 3.12+, aiogram 3.x, PostgreSQL + SQLAlchemy 2.0 async + asyncpg, Alembic, Redis (FSM storage), pydantic-settings.
Разработка на Windows (Redis в WSL). Зависимости фиксировать полностью (requirements с версиями или uv/poetry lock).
Docker не используем — никогда и ни при каких обстоятельствах; прод собирается вручную на VPS.
VPN-туннель до Telegram настраивается позже отдельно; сейчас задача — только функционал бота.

## Функционал MVP
MVP — афиша + личный кабинет для старта маркетинга. Записи/заявок внутри бота нет.
Пользователь:
- /start с диплинками: `src_<code>` (источник трафика: листовки QR, сайт, VK, Instagram, TG-канал), `ref_<code>` (реферал), `inv_<token>` (приглашение, FULL). Каждый заход пишется в client_source_touches.
- Экран согласий: ПД (обязательно) и рекламные рассылки (отдельно, опционально). Тексты — из legal_documents.
- Короткая регистрация: телефон кнопкой «Поделиться контактом», ФИО (одно текстовое поле, подтверждение для сертификата), специальности, должность. Остальное — дозаполнение в кабинете.
- Личный кабинет: профиль и редактирование, реферальная ссылка + счётчик.
- Расписание (просмотр): ближайшие потоки, карточка, программа, даты/время по дням, площадка, тарифы.
  Под каждым курсом — кнопка записи, которая открывает диалог с менеджером (ссылку на менеджера пользователь даст позже).
- Заявки, «Мои заявки», «Сообщить о наборе» — код есть, но выключены (APPLICATIONS_ENABLED=false) до полной версии.
- О центре / контакты / связаться с менеджером.
Админ (роли из таблицы admins, owner — из .env):
- Справочники: лекторы, площадки, специальности, должности.
- Мастер «Новый курс» (programs) и мастер «Новый поток» (sessions + session_days + тарифы + лекторы), кнопка «Скопировать прошлый поток».
- Уведомление менеджерам о новой заявке, смена статуса заявки.
- /stats: новые пользователи по дням и по источникам, заявки. Экспорт клиентов в CSV.
- Генерация ссылок источников (acquisition_sources).

## Обязательные правила (выводы из ревью старого бота)
- Фильтр админа на уровне всего админ-роутера (message и callback_query), не на отдельных хендлерах.
- Любой пользовательский текст в HTML — через html.escape. Длинные тексты не в caption (лимит 1024), при необходимости фото и текст отдельно.
- FSM-шаги, ожидающие текст, должны корректно обрабатывать фото/стикеры/голос.
- Глобальный обработчик ошибок `dp.errors`, без глотающих middleware.
- Никаких ПД и секретов в логах и print(). INFO на проде.
- Имя бота для ссылок — из `await bot.me()`, не хардкод.
- Только Alembic-миграции; create_all / DROP SCHEMA на проде запрещены. Naming convention в MetaData.
- Callback data — через `CallbackData`-фабрики, не строки со split.
- Любая inline-кнопка меняет то сообщение, в котором нажата (насколько позволяют aiogram/Telegram): текст→текст,
  фото→фото — правка; фото↔текст или сообщение удалено — удалить старое и прислать новое.
- Расписание — карусель со стрелками ◀️ n/N ▶️ (обязательно).
- Слой доступа к данным: репозитории/сервисы по доменам; сессия БД на апдейт через middleware. Хендлеры без SQL.
- Нет копипасты однотипных редакторов полей — generic-реализация.
- Проверять результаты операций (запись на поток, дубликаты, статус потока).
- Время — TIMESTAMPTZ, Europe/Moscow в интерфейсе; деньги в копейках; enum через native_enum=False.

## Порядок работы
1. Скелет проекта: структура пакетов, конфиг, логирование (Postgres локально, Redis в WSL — без Docker).
2. Модели MVP-таблиц строго по docs/01_db_plan.md + первая миграция Alembic + сиды справочников.
3. Регистрация, согласия, источники → кабинет → расписание и заявки → админка → статистика.
Перед каждым этапом кратко предложить план и дождаться подтверждения.
